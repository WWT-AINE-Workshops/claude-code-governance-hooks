# Lab 3: The big red button

**SDLC phase:** Operate · **Stage:** Agent Augmented · **Time:** 40 minutes

## Why this matters

Positive control means you can halt agent work whenever governance says so, and prove that you can. A security incident, a vendor outage or an audit finding should be able to stop every session, from outside it, in seconds.

Tasklane's team has a control plane, a small service that holds one status: run, halt, or suspend named tools. They also have a draft kill switch hook, `.claude/hooks/killswitch.mjs`, that asks the control plane before every prompt and tool call. In this lab you turn it on, drill it, find out what happens when the control plane itself is down, and fix that. Then you write the managed settings that make sure nobody can switch it off.

You need two terminals for this lab: one for the control plane, one for commands. In the CLI: run `claude` in a third terminal, from the repo root, wherever a step says to start a new session in the Code tab.

## Before you start

Run the reset script from the repo root, in a terminal.

```bash
./scripts/reset-lab.sh 3
```

What this does: switches you to a branch called `lab-3` at the start of this lab, with Labs 1 and 2 already fixed, and resets the app's local data. It stops if you have uncommitted changes: commit your Lab 2 work first.

## Steps

### Step 1: Pick the control for each need

**Do this.** For each need, choose the best control from this list: permission deny rule, permission ask rule, PreToolUse command hook, `disableBypassPermissionsMode`, `allowManagedHooksOnly`. Write your answers in the workbook, or on paper.

```text
1. Claude is never allowed to read .env files.
2. Stop scripts fetched from the internet being piped into a shell.
3. Every git push needs a person to approve it.
4. Bypass mode cannot be turned on by anyone.
5. Only hooks that security has approved are allowed to run.
```

**What you should see.** Check your answers:

1. A deny rule: a simple pattern, enforced natively.
2. A PreToolUse command hook: a pipe can be written many ways, so it needs logic.
3. An ask rule, or a hook that answers ask.
4. `disableBypassPermissionsMode`: it removes the escape hatch.
5. `allowManagedHooksOnly`: it stops hooks nobody approved.

**Why.** When a pattern is enough, reach for a permission rule. When you need logic or state from outside, reach for a hook. A kill switch needs outside state.

### Step 2: Turn the kill switch on

**Do this.** In your first terminal, start the control plane and leave it running.

```bash
npm run control-plane
```

What this does: starts the control plane on port 3002, in run mode. It writes nothing to disk. Stop it later with `Ctrl+C`.

In the Code tab, start a new local session in your `my-claude-code-governance-hooks` folder, and send this prompt:

```prompt
Register .claude/hooks/killswitch.mjs in .claude/settings.json on UserPromptSubmit and on PreToolUse, with node and the CLAUDE_PROJECT_DIR path in args, like the other hooks. Use a timeout of 5. Do not change the hook itself.
```

In the CLI: run `claude` from the repo root, then send the same prompt.

Then start another new session in the Code tab, in the same folder, and send this prompt:

```prompt
Run npm test five times, one after another. Wait 10 seconds between runs with sleep 10. Run each npm test and each sleep as a separate command, not in one line, and give me a one-line summary after each run.
```

**What you should see.** `.claude/settings.json` has the kill switch under `UserPromptSubmit` and `PreToolUse`. In the new session, Claude starts the first test run. Go straight to the next step while it works. If you have a moment first, run `npm run hooks:try -- killswitch` in your second terminal: it ends with `8 of 11 PASS`, with both settings checks passing.

**Why.** UserPromptSubmit checks before Claude sees a prompt. PreToolUse checks before every tool call. Between them, a halt lands on the next prompt or the next tool call, whichever comes first.

### Step 3: Drill it, and time it

**Do this.** In your second terminal, while Claude is working, halt every session.

```bash
npm run halt -- --reason "drill"
```

What this does: sets the control plane to halt, with your reason, and prints the time. It changes no file.

Note the time it prints. When the session stops, note that time too. Then send any prompt in the session, and read what you get back. Finally, resume.

```bash
npm run resume
```

What this does: sets the control plane back to run. It changes no file.

**What you should see.** The session stops at its next tool call, before the next `npm test` or `sleep` starts, and shows the stop reason, which includes "Halted by governance: drill". If Claude had already finished, the halt lands on your next prompt instead. A new prompt is stopped the same way, before Claude sees it. After `npm run resume`, a new prompt works again.

**Why.** Positive control is something you can show, with a number. The seconds between the halt and the stop are your halt time.

### Step 4: Take the control plane away

**Do this.** In your first terminal, stop the control plane with `Ctrl+C`. Then send this prompt in the Code tab:

```prompt
List the files in the tools folder.
```

Now run the kill switch fixtures in your second terminal.

```bash
npm run hooks:try -- killswitch
```

What this does: runs the kill switch against stand-in control planes that are up, halted, down, broken and hanging, then checks the settings. It changes nothing.

**What you should see.** Claude lists the files: with nobody to ask, the kill switch let the session carry on. The fixtures end with `8 of 11 PASS`. The ones that fail are control plane down, a 500 error and a control plane that hangs.

**Why.** This is the trap. A kill switch that fails open stops working at the exact moment you might need it, when the service behind it is in trouble.

### Step 5: Make it fail closed

**Do this.** Start the control plane again in your first terminal, so the session can keep working while you fix the hook.

```bash
npm run control-plane
```

What this does: starts the control plane again, in run mode.

Then send this prompt in the Code tab:

```prompt
Fix .claude/hooks/killswitch.mjs so it fails closed. Give the request to the control plane a 2-second timeout. If it fails, times out, returns a non-2xx status or an unknown mode, return continue false with a stopReason that says the control plane did not answer. Let KILLSWITCH_FAIL_MODE=open turn that off for one terminal. In .claude/settings.json, add "onFailure": "block" to both kill switch handlers. Then run npm run hooks:try -- killswitch.
```

When Claude has finished, stop the control plane with `Ctrl+C` again, and send this prompt:

```prompt
List the files in the tools folder.
```

**What you should see.** The fixtures end with `11 of 11 PASS`. With the control plane stopped, the session halts, and the reason says the control plane did not answer.

**Why.** Fail closed is a choice you make on purpose. Write down who owns it, and when fail open is allowed.

### Step 6: Lock it in with managed settings

**Do this.** Start the control plane again in your first terminal.

```bash
npm run control-plane
```

What this does: starts the control plane again, in run mode, so your sessions can work.

Open `managed/managed-settings.json`. It is the draft your IT team would ship to every laptop. Then send this prompt in the Code tab:

```prompt
Complete managed/managed-settings.json. Set allowManagedHooksOnly and allowManagedPermissionRulesOnly to true. Under permissions, set disableBypassPermissionsMode to "disable", keep the deny rules, add Read(**/.env.*), and add an ask rule for Bash(git push *). Register the hooks from /opt/claude-governance/hooks/: the kill switch on UserPromptSubmit and PreToolUse with a timeout of 5, the guard on PreToolUse for Bash|Read, and the audit hook on PostToolUse and PostToolUseFailure. Give the kill switch and the guard "onFailure": "block". Then run npm run hooks:try -- managed.
```

**What you should see.** `managed/managed-settings.json` has the three lock-down keys, the deny and ask rules and four hook events. The check ends with `10 of 10 PASS`.

**Why.** A guard in a project file can be edited or deleted by anyone with the repo. Managed settings win over every other level, their hooks cannot be removed from below, and `disableAllHooks` in a user or project file cannot turn them off.

### Step 7: Read which file wins

**Do this.** If you are short of time, read this step after the session. Read this table, from the highest precedence to the lowest. Then answer the question below it, in the workbook.

```text
1. Managed settings      (IT ships it; nothing below can override it)
2. Command line flags    (for one session)
3. Local project         (.claude/settings.local.json, yours only)
4. Shared project        (.claude/settings.json, in git)
5. User                  (~/.claude/settings.json)
```

Question: your kill switch lives in `.claude/settings.json` today. Name two ways it could stop protecting you.

**What you should see.** Two good answers: someone edits or deletes the shared project file, and a project that never had the file has no kill switch at all. With `allowManagedHooksOnly`, the managed copy is the only one that runs, so neither can happen.

**Why.** End-state thinking: decide the policy you want everywhere, then ship it where it cannot be removed.

## You're done when

`npm run hooks:try -- killswitch` ends with `11 of 11 PASS`, `npm run hooks:try -- managed` ends with `10 of 10 PASS`, and you have a halt time. Post `Lab 3: halt in N seconds` in the chat.

## If it goes wrong

- **Every prompt halts with "the control plane did not answer".** That is the fixed kill switch doing its job. Start the control plane with `npm run control-plane`. To work without it in one terminal, start the CLI with `KILLSWITCH_FAIL_MODE=open` set. The Code tab has no per-terminal setting: start the control plane, or remove the kill switch. To turn it off for good, remove the kill switch from `.claude/settings.json` by hand.
- **`npm run halt` says the control plane is not answering.** Start it in your first terminal. If port 3002 is busy, close the program that uses it.
- **The halt does not land.** Check that `.claude/settings.json` has the kill switch under both events, then start a new session.
- **Claude ran `npm run resume` itself during a suspend.** The lab's control plane trusts anyone on your laptop. See the last stretch goal.
- To leave the CLI, press `Ctrl+D` twice on an empty prompt.

## Stretch goals

- Install the managed file for real. It needs admin rights. On macOS the path is `/Library/Application Support/ClaudeCode/managed-settings.json`, and on Linux and WSL it is `/etc/claude-code/managed-settings.json`. Copy the three hooks to `/opt/claude-governance/hooks/`, start a new session in the CLI, and run `/status` to see which managed source Claude Code picked. Remove both again when you are done.
- Suspend one tool, not everything. Run the command below, then ask Claude to fetch a web page, and then to run the tests.

  ```bash
  npm run suspend -- --tool WebFetch --reason "vendor incident"
  ```

  What this does: sets the control plane to suspend WebFetch only. It changes no file. Run `npm run resume` when you are done.

- During a suspend, Claude can still run Bash. Ask Claude to add a rule to the guard that blocks any Bash call that talks to the control plane, so an agent cannot resume itself.
- Write your team's fail-mode decision in one line, with its owner. Fail closed, fail open, or it depends, as long as it is written down.

## Recap

You halted a live session from outside it, timed it, and found that the first version of the kill switch failed open when its control plane went down. You made it fail closed, and wrote the managed settings that make sure nobody can remove it.

After the session, the fixed kill switch is still registered in this repo, so every prompt here halts when the control plane is down. To keep working in this folder, start it with `npm run control-plane`, or remove the kill switch from `.claude/settings.json` by hand and commit that.
