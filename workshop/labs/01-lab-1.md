# Lab 1: A guardrail that fails closed

**SDLC phase:** Secure & Release · **Stage:** Agent Augmented · **Time:** 40 minutes

## Why this matters

Tasklane is a small task-tracking API. Its team has already added a guard for Claude Code: a PreToolUse hook, `.claude/hooks/guard.mjs`, that runs before every Bash and Read call. It is meant to refuse destructive commands and keep secrets such as `.env` out of the session. It prints "Blocked by policy" when it sees one.

It looks like it works. It does not. In this lab you prove that, fix it so it fails closed, and then break it on purpose to see what still protects you.

A hook is code that Claude Code runs at a set point, every time. The model cannot talk its way past it. But a hook only blocks if it answers in the one way Claude Code reads as "no".

## Before you start

Run the reset script from the repo root, in a terminal.

```bash
./scripts/reset-lab.sh 1
```

What this does: switches you to a branch called `lab-1` at the start of this lab, and resets the app's local data. It stops if you have uncommitted changes, and lists them.

Keep this terminal open. You will run the lab's helper commands in it, and talk to Claude Code in the desktop app's Code tab. In the CLI: wherever a step says to start a new session in the Code tab, run `claude` in a second terminal, from the repo root.

## Steps

### Step 1: Try the guard without Claude

**Do this.** Feed the guard its saved test inputs. Each one is a tool call Claude might make, with the verdict the guard should give.

```bash
npm run hooks:try -- guard
```

What this does: runs `.claude/hooks/guard.mjs` once per file in `tools/fixtures/guard/` and compares what it did with what it should do. It changes nothing.

**What you should see.** Twelve lines, each starting PASS or FAIL, and a last line that says `3 of 12 PASS`. Nine fixtures FAIL with "expected block, got allow", among them the `rm -rf`, `.env`, force-push and malformed-input ones. Each reason says exit 1 is a non-blocking error.

**Why.** You can test a hook in a second, with no model in the loop. That makes it something you can check in CI, like any other code.

### Step 2: See it fail in a real session

**Do this.** In the Claude desktop app, open the Code tab and start a new local session in your `my-claude-code-governance-hooks` folder. If it asks whether you trust the folder, say yes. Then paste this into the prompt box and press Enter:

```prompt
Show me what is in the .env file in this folder.
```

In the CLI: run `claude` from the repo root, then send the same prompt.

**What you should see.** Claude reads `.env` and shows its demo values, even though the guard printed "Blocked by policy". You may see a hook error notice that names the PreToolUse hook. If Claude refuses on its own, or the notice does not show, carry on: step 1 already showed the same thing.

**Why.** The guard saw the risk and said so, and the call still ran. A warning is not a control.

### Step 3: Find out why

**Do this.** In the same session, send this prompt:

```prompt
Read .claude/hooks/guard.mjs. Explain why it prints "Blocked by policy" but the Read call still runs. Also tell me what happens if the hook gets input it cannot parse. Do not change any files yet.
```

**What you should see.** Claude points at the exit code the guard uses to block. It explains that Claude Code only treats exit 2, or a deny decision in JSON, as a block. Any other exit code is an error that lets the call through. It also notes that bad input crashes the script, which is an error too. The wording differs from run to run.

**Why.** Most of us learned that any non-zero exit means "stop". In a hook, only exit 2 does.

### Step 4: Make it fail closed

**Do this.** Send this prompt:

```prompt
Fix .claude/hooks/guard.mjs so it fails closed. Block with exit code 2 and put the reason on stderr. Wrap the whole check so that any error, including input it cannot parse or a call with no tool input, is blocked too. Keep the existing rules and the node_modules/.cache exception. Then run npm run hooks:try -- guard and show me the result.
```

**What you should see.** Claude edits the guard and runs the fixtures. The last line says `12 of 12 PASS`. Run it yourself in your terminal to be sure.

```bash
npm run hooks:try -- guard
```

What this does: runs the fixtures again. It changes nothing.

**Why.** A guard that crashes open is worse than no guard: it makes you feel safe.

### Step 5: Use a rule where a rule will do

**Do this.** Reading `.env` with the Read tool is a simple pattern, and Claude Code can enforce it without any script. Send this prompt:

```prompt
Add a permissions deny list to .claude/settings.json with Read(**/.env), Read(**/.env.*) and Read(**/secrets/**), so they apply at any depth in the project. Also make the guard's secret-path check catch names with more than one dot, such as .env.prod.local. Keep the hooks as they are.
```

Then start a new session in the Code tab, in the same folder, and send this prompt:

```prompt
Show me what is in the .env file in this folder.
```

**What you should see.** `.claude/settings.json` now has a `permissions` block with three deny rules. In the new session, Claude cannot read `.env`, and says it was blocked. Your fixed guard would refuse it too, so now two controls cover it: the rule would keep working even if the guard broke.

**Why.** If a pattern can say it, use a permission rule: it is native and needs no code. Keep the hook for logic a pattern cannot express, such as the many ways to write `cat .env` in a shell.

### Step 6: Break it on purpose

**Do this.** Open `.claude/settings.json` in your editor. In the guard's `args`, change `guard.mjs` to `guard-old.mjs`, a file that does not exist, and save. In the Code tab session, send this prompt:

```prompt
Run ls -la in this folder.
```

Now, in the guard's handler in `.claude/settings.json`, put a comma after `"timeout": 10`, and add `"onFailure": "block"` on a new line under it, with no comma after it. Save, and send the same prompt again.

Finally, change `guard-old.mjs` back to `guard.mjs`, keep the `onFailure` line, and save.

**What you should see.** The first time, `ls -la` runs and lists the folder. You may see a hook error that says the guard script was not found: the guard never ran, so it could not have stopped anything.

The second time, the same harmless call is blocked, and you may see an error about the hook. The exact wording differs between versions.

Fallback: on a Claude Code version before 2.1.295, `onFailure` is ignored and the call is not blocked. Note that, and move on.

**Why.** A typo in a settings file silently turns a guard off, and the script cannot catch an error it never gets to run. `onFailure` makes the config fail closed too. Lab 3 makes sure nobody can remove the guard at all.

## You're done when

`npm run hooks:try -- guard` ends with `12 of 12 PASS`, `.claude/settings.json` has the three deny rules and `"onFailure": "block"` on the guard, and Claude cannot read `.env`. Post `Lab 1: 12 of 12` in the chat.

Then commit your work in the terminal, so Lab 2's reset can start cleanly.

```bash
git add -A
```

What this does: stages every change you made in this lab. It changes no file.

```bash
git commit -m "lab 1: guard fails closed"
```

What this does: records the staged changes on your `lab-1` branch.

## If it goes wrong

- **Every Bash and Read call is blocked, even `ls`.** The guard's path is still wrong and `onFailure` is on. Fix the path in `.claude/settings.json` by hand: Claude cannot read files to fix it for you.
- **Step 2: Claude will not read `.env`.** Some sessions decline on their own. That is the model being careful, not the guard. Step 1's output shows the same gap.
- **`npm run hooks:try -- guard` says a fixture expected allow and got block.** The fix is too strict. Ask Claude to keep `ls -la`, reading a source file and the `node_modules/.cache` clean-up allowed.
- **The new deny rules seem to be ignored.** Start a new session. Settings are read when a session starts, and normally reloaded when the file changes.
- To leave the CLI, press `Ctrl+D` twice on an empty prompt.

## Stretch goals

- Ask Claude to make the guard rewrite `npm run deploy` to add `--dry-run`, with `updatedInput` and an allow decision. Try it with a prompt that asks Claude to deploy.
- Make `git push` need a human: first with an `ask` decision from the guard, then with an ask rule, `Bash(git push *)`. Which one would you rather maintain? The docs note that the rule does not match `git -C . push`, so test that too.
- Add a fixture for something the guard misses, such as a downloaded script piped into a shell. Watch it fail, then make it pass.

## Recap

The guard said "blocked" and allowed everything, because only exit 2 or a deny decision blocks. You made the script fail closed, moved the simple pattern into a deny rule, and saw that a mistyped path turns any hook off unless the config fails closed too.
