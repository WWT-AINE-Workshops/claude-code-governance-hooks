# Lab 2: Receipts you can trust

**SDLC phase:** Secure & Release · **Stage:** Agent Augmented · **Time:** 40 minutes

## Why this matters

Lab 1 was the bouncer at the door. This lab is the receipt. A PostToolUse hook runs after a tool call has happened. It cannot stop anything, but it can record what happened, so you have evidence when someone asks.

Tasklane already has an audit hook, `.claude/hooks/audit.mjs`. It writes one line per tool call to `.audit/audit.jsonl`. As evidence, it has three problems: it copies secrets into the log, it misses every call that fails, and anyone can edit a line without it showing. You find all three, then fix them.

## Before you start

Run the reset script from the repo root, in a terminal.

```bash
./scripts/reset-lab.sh 2
```

What this does: switches you to a branch called `lab-2` at the start of this lab, with Lab 1's fixed guard already in place, and resets the app's local data. It stops if you have uncommitted changes: commit your Lab 1 work first.

Then clear the audit log from Lab 1, so you start with an empty one.

```bash
rm -f .audit/audit.jsonl
```

What this does: deletes only the local audit log, which git ignores. It changes no tracked file.

In the CLI: wherever a step says to start a new session in the Code tab, run `claude` in a second terminal, from the repo root.

## Steps

### Step 1: Make some activity

**Do this.** In the Code tab, start a new local session in your `my-claude-code-governance-hooks` folder, and send this prompt:

```prompt
Read config/vendor.json and tell me which region the bucket is in. Then run npm run migrate, even if you think it will fail, and tell me what happened.
```

In the CLI: run `claude` from the repo root, then send the same prompt.

**What you should see.** Claude reads the file and names the region. Then `npm run migrate` fails, because the project has no such script. That failure is on purpose.

**Why.** You need one call that succeeds with a secret in its output, and one call that fails.

### Step 2: Read the receipts

**Do this.** In your terminal, show the last lines of the log.

```bash
tail -n 5 .audit/audit.jsonl
```

What this does: prints the last five lines of the audit log. It changes nothing.

Then check the log the way an auditor would.

```bash
npm run audit:verify
```

What this does: checks the log's hash chain and reports the first line that breaks it. It changes nothing.

**What you should see.** Three problems. The line for the Read call contains the fake key that starts `AKIAIOSFODNN7`. There is no line at all for `npm run migrate`. And `audit:verify` says the chain is broken at line 1 because the records have no `prev` and `hash` fields, so an edit cannot be detected.

**Why.** A log that leaks secrets becomes a new place to steal them from. A log that misses failures misses the most interesting attempts. A log anyone can edit is not evidence.

### Step 3: Try the hook without Claude

**Do this.** Run the audit fixtures.

```bash
npm run hooks:try -- audit
```

What this does: runs the audit hook on saved inputs, into a temporary folder, then checks each record, the chain and the settings. It changes nothing in your folder.

**What you should see.** Nine checks and `1 of 9 PASS`. The failures say a secret is in the log, `prompt_id` and `event` are missing, the chain is broken, and `audit.mjs` is not registered on `PostToolUseFailure`.

**Why.** Now you have a test that says exactly what "fixed" means.

### Step 4: Fix the hook

**Do this.** Send this prompt in the Code tab:

```prompt
Fix .claude/hooks/audit.mjs. Before writing anything, redact AWS access key ids, AWS secret keys, GitHub tokens and private keys from the tool input, the tool response and the error. That includes a 40-character AWS secret key on a line of its own with no label next to it, the way jq -r prints it. Add event (from hook_event_name), prompt_id, tool_use_id and error to each record. Chain the records the way tools/audit-chain.mjs checks them: prev is the hash of the record before it, or GENESIS for the first, and hash is the SHA-256 of the record without its hash field. Take a lock while you append, so two hooks at once cannot break the chain, and remove a lock older than two seconds, so a crashed hook cannot block the rest. Never block: catch every error and only report it on stderr. Then run npm run hooks:try -- audit.
```

**What you should see.** Claude edits `audit.mjs` and runs the fixtures. They end with `8 of 9 PASS`. `settings-PostToolUseFailure` still fails: that is the next step.

Fallback: if Claude is still on the hash chain after seven minutes, add this code to `audit.mjs` in your editor. It matches what `audit:verify` checks:

```js
import { createHash } from 'node:crypto';
import { appendFileSync, existsSync, readFileSync } from 'node:fs';

const GENESIS = '0'.repeat(64);
const hashOf = (record) => createHash('sha256').update(JSON.stringify(record)).digest('hex');
const lastHash = (file) => {
  const last = existsSync(file) ? readFileSync(file, 'utf8').trim().split('\n').at(-1) : '';
  try {
    return JSON.parse(last).hash ?? GENESIS;
  } catch {
    return GENESIS;
  }
};

// Build the record with every field, and prev: lastHash(file). Then append it:
// appendFileSync(file, `${JSON.stringify({ ...record, hash: hashOf(record) })}\n`);
```

**Why.** Redact before you write, because a secret that reaches the disk is already leaked.

### Step 5: Catch the failures too

**Do this.** Send this prompt:

```prompt
Register the audit hook on PostToolUseFailure in .claude/settings.json, the same way it is registered on PostToolUse. Then run npm run hooks:try -- audit.
```

**What you should see.** `.claude/settings.json` has a `PostToolUseFailure` entry that runs `audit.mjs`, and the fixtures end with `9 of 9 PASS`.

**Why.** PostToolUse only fires when a tool succeeds. Failed calls fire PostToolUseFailure, so an audit that listens to one event misses half the story.

### Step 6: Prove it, then tamper with it

**Do this.** Clear the log in your terminal.

```bash
rm -f .audit/audit.jsonl
```

What this does: deletes only the local audit log, which git ignores.

Then start a new session in the Code tab, and send this prompt:

```prompt
Read config/vendor.json and tell me which region the bucket is in. Then run npm run migrate, even if you think it will fail, and tell me what happened.
```

Check the new log.

```bash
npm run audit:verify
```

What this does: checks the hash chain. It changes nothing.

Now open `.audit/audit.jsonl` in your editor. On line 1, change one character inside the record, for example a letter of the file path, and save. Check again.

```bash
npm run audit:verify
```

What this does: checks the hash chain again. It changes nothing.

**What you should see.** The first check says `Chain intact` with the number of records. The fake key is now `[REDACTED]`, and there is a record with event `PostToolUseFailure` for `npm run migrate`. After your edit, the check says the chain is broken at line 1.

**Why.** A hash chain does not stop an edit. It makes an edit show. To stop someone deleting the whole file, the records have to leave the laptop, which is a stretch goal.


## If it goes wrong

- **The log is empty after step 1.** Each tool call writes a line only once the session has picked up the hook. Start a new session in the same folder and send the prompt again.
- **`audit:verify` says the chain is broken at line 1 after the fix.** The log still holds old records from before the fix. Clear it with `rm -f .audit/audit.jsonl` and make new activity.
- **Claude's session seems slow after the fix.** Each tool call now waits for the lock. If a crashed hook left `.audit/.lock` behind, the hook removes it after two seconds.
- **The guard from Lab 1 blocks a command you need.** Read the reason it gives. It is working as designed; ask Claude for another way.
- To leave the CLI, press `Ctrl+D` twice on an empty prompt.

## Stretch goals

- Redact what Claude sees too, not only what you log. A PostToolUse hook can return `updatedToolOutput` to change the output Claude gets from any tool. Ask Claude to add that for key-shaped strings. The tool has still run, so the file still holds the key.
- Send each record somewhere a user cannot delete it, as well as to the file. Talk with a neighbour about where that would be in your company.
- If your team already sends Claude Code telemetry, find one of your records' `prompt_id` values in it. The docs say it matches the `prompt.id` attribute on Claude Code's OpenTelemetry events, so a hook record and a telemetry event join on one key.

## Recap

A PostToolUse hook is evidence, not prevention. You made the evidence safe to keep (redacted), complete (failures too) and tamper-evident (a hash chain), and you proved each one with a check you can run in a second.
